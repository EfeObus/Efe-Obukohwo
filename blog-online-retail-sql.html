The Query Ran, But Was It Right?

July 2026 10 min read Efe Obukohwo
PostgreSQL Window Functions Data Quality SQL

It's easy to treat a SQL query as done the moment it returns rows without an error. No red text, no exception — must be correct. That assumption is exactly what breaks real analysis, and it's what I set out to stress-test with this project: a normalized PostgreSQL database and 30 production queries over 500,000+ e-commerce transactions, where I deliberately went back and audited my own outputs instead of trusting a clean execution.

I found three real bugs in my own analysis. Here's what happened, and why I think the auditing mattered more than the queries themselves.

📊 The Dataset

The UCI Online Retail dataset: 500,000+ line items from a UK-based gift and homeware wholesaler, December 2010 to December 2011. £8.91M in revenue, 4,339 customers, 38 countries — and 25% of rows missing a CustomerID entirely.

Schema First, Queries Second

The raw export is a single flat CSV — one row per product line per invoice, no relationships, no keys. Before writing a single analytical query, I normalized it into five core tables (countries, customers, products, invoices, invoice_details) plus a staging table holding the untouched original import, so every derived number can be traced back to source. Third normal form, surrogate keys, indexed foreign keys — the boring part of the project, and the part that made everything after it possible to trust.

Thirty Queries, One Running-Total Example

The 30 queries span customer segmentation (RFM, LTV quartiles via NTILE), product performance and cross-sell pairs, temporal patterns, and anomaly detection. Window functions carry most of the weight — here's cumulative revenue by country using SUM() OVER (PARTITION BY ... ORDER BY ...), one query, no procedural loop needed:

WITH daily_country_revenue AS (
  SELECT DATE(i.invoice_date) AS sale_date,
         co.country_name,
         ROUND(SUM(id.line_total)::NUMERIC, 2) AS daily_revenue
  FROM invoices i
  JOIN invoice_details id ON i.invoice_id = id.invoice_id
  JOIN customers c ON i.customer_id = c.customer_id
  JOIN countries co ON c.country_id = co.country_id
  GROUP BY DATE(i.invoice_date), co.country_name
)
SELECT sale_date, country_name, daily_revenue,
       SUM(daily_revenue) OVER (
         PARTITION BY country_name ORDER BY sale_date
       ) AS cumulative_revenue
FROM daily_country_revenue
ORDER BY country_name, sale_date;

The findings this surfaced were real and specific: 82% of revenue from the UK alone, the top 10% of customers driving 61% of revenue (a moderate concentration, not the textbook 80/20), and — the one that reframes the whole business — sub-£5 products generating 71% of revenue while £25+ items are only 2.8%. This is a volume business built on cheap, high-frequency items, not a margin business, and that single finding changes what "optimize revenue" should even mean for this company.

Then I Stopped Trusting My Own Output

A query that runs without error and a query that's correct are two different claims. So instead of stopping at "the queries executed," I went back through the exported results and checked them against what I actually expected to see — and found three problems that a green checkmark would never have caught.

Bug 1: Every Customer Was "Inactive"

My recency segmentation compared purchase dates to CURRENT_DATE — a totally reasonable pattern in a live application. But this is a static, historical dataset ending in December 2011. Every customer's "days since last purchase" was therefore 5,000+ days, and the query dutifully labeled 100% of customers as "Inactive." The label wasn't wrong, exactly — it was just computed against the wrong reference point, and it carried zero analytical information as a result. The fix is one line: anchor recency to (SELECT MAX(invoice_date) FROM invoices) instead of today's date.

Bug 2: A Retention Curve That Was Never Actually Computed

The cohort analysis query was designed to show retention across months 0, 1, 2, 3, 6+ after a customer's first purchase. The actual exported result had exactly 13 rows — one per signup month, every single one at month zero. The month-over-month retention curve the query was built to produce simply never appeared in the output. If I'd only glanced at "13 rows, looks like cohort data" and moved on, I'd have been one confident sentence away from quoting a retention curve that was never actually there.

Bug 3: An Anomaly Filter That Flagged Everyone

My STDDEV-based outlier detection, tuned to a 1.5 standard deviation threshold, flagged 3,396 of 3,754 customers — 90% — as "High Volume Spikes." A filter that flags nine out of every ten data points isn't a filter. Rather than quietly shipping that number, I documented it as a known limitation with the actual fix (tightening to 2–3 STDDEV) rather than letting a technically-executed query imply a finding it didn't support.

What I Assumed What Was Actually True
Query ran without error = result is trustworthy 3 of ~5 "advanced" queries had a logic bug invisible without checking real output
CURRENT_DATE is a safe default for recency Only true for live data — a historical dataset needs a fixed reference date
A returned row count that "looks right" confirms correctness 13 rows looked plausible for 13 cohort months; it was actually 13 wrong rows

Why This Is the Part Worth Talking About

Anyone can learn RANK(), LAG(), and a CTE syntax from documentation. What's harder to teach — and what I think actually separates a portfolio SQL project from production-grade analysis — is the discipline to go back and ask "does this number actually mean what I think it means?" before it goes in front of a stakeholder. Every one of these three bugs would have produced a plausible-looking, wrong answer if I'd shipped the first version. Documenting them wasn't an afterthought to the project; it was the project working as intended.
