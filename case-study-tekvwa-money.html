TEKVWA Money

Full-Stack Personal Finance Platform

2026 – Present Web · Android · iOS Live Plaid Integration

The Problem

TEKVWA Money exists to solve financial leakage — the silent loss of money through small, frequent, unnoticed expenses. Many people earn a decent income but still struggle to save, not from a lack of discipline but from a lack of visibility into where the money is actually going. Most existing budgeting tools make this worse by demanding bank connections, complex categorization systems, or constant manual entry before they deliver any value.

Design Philosophy

Make financial tracking require almost no ongoing effort, and let the app do the noticing — automatic bank statement imports, self-learning categorization, budget-aware alerts, and AI-narrated summaries, instead of asking the user to build a new habit from scratch.

What It Is

A full-stack personal finance application built with React, Express.js, PostgreSQL, Zustand, and Tailwind CSS, shipped as a website and as native Android and iOS apps from a single Capacitor-wrapped codebase. Users can record income and expenses, import bank statements, link a real bank account, set budgets, monitor spending alerts, and generate exportable financial reports — all live in production, not a demo build.

Core Features

Connect Bank (Plaid)

Real bank-account linking running against Plaid's Production environment on web, Android, and iOS. New transactions sync in about once a day, auto-categorized with no manual review step.

Statement Import

PDF/CSV/XLSX upload across 24+ Canadian banks and credit unions, with duplicate detection and category corrections remembered for future imports.

Gemini AI Insights

Daily/weekly/monthly spending narratives via Vertex AI. The model only ever narrates numbers the app already computed deterministically — never asked to calculate anything itself.

Budget-Driven Alerts

Spending warnings at 70%, 85%, and 100%+ thresholds, deduplicated so an alert escalates once per period instead of firing on every subsequent transaction.

Biometric App Lock

Face ID/fingerprint gates the native apps on open or resume, independent of the login session, with the token secured behind Android Keystore / iOS Keychain.

Full RBAC

Customer, Staff (Support/Finance Analyst/Auditor), Admin, and Super Admin roles, each with a dedicated dashboard and an operational audit trail.

One Codebase, Two Very Different Platforms

Capacitor wraps the same React build into real native Android and iOS projects — the production bundle compiled directly into each app, talking to the production API rather than a dev proxy. But the platforms don't behave identically underneath, and the app has to know about the gaps explicitly:

  • iOS's WKWebView URL scheme limitation: iOS reserves the http/https schemes for real remote pages, so it silently falls back to capacitor://localhost regardless of config. The backend's CORS allowlist and origin-checking middleware both account for this explicitly — including reconstructing the origin from protocol + host, since the WHATWG spec returns the literal string "null" for .origin on non-special schemes like capacitor:.
  • Safe-area insets: the iPhone's Dynamic Island needs both a viewport-fit=cover meta tag and matching env(safe-area-inset-*) CSS applied directly to every fixed-position full-screen element (the lock screen, notification center, mobile sidebar) — body padding alone doesn't reach anything with position: fixed.
  • Biometric prompt resume race: presenting Face ID briefly resigns and reactivates the app as part of showing its own system UI, which used to race against the app's own resume-triggered lock listener — occasionally re-locking the screen the instant it had just unlocked. Fixed with an explicit "unlock in flight" guard rather than trying to out-time the race.
  • CocoaPods, not Swift Package Manager: the biometric plugin ships only a .podspec, no Package.swift — SPM would silently drop it instead of failing the build.

Security

  • Hybrid session transport: an httpOnly/Secure/SameSite=Lax cookie on web (never readable by page scripts), a Bearer token on native — cookies aren't reliable cross-origin inside a Capacitor WebView
  • Plaid access tokens encrypted at rest; AI Insights authenticate via Application Default Credentials rather than a stored API key
  • Password hashing with bcrypt, server-side input validation on every write endpoint, and a configurable account-lockout threshold after repeated failed logins
  • A Super Admin-only Plaid Sandbox evaluation page, completely walled off from the customer-facing flow, for testing without ever touching a real connection

Known Limitations

Documented rather than hidden, since this is a real production app, not a polished demo:

  • No iOS push notifications yet — needs a paid Apple Developer Program membership to generate the APNs key. The client-side registration code already runs on iOS and is harmless; push will work with no further code changes once that's available. Android push is live today.
  • Offline transaction queuing is live code, not manually verified — it's actively wired into the Income/Expense stores and queues correctly, but hasn't had a deliberate airplane-mode test pass on a real device yet.
  • No frontend test suite — the backend has a real vitest + supertest suite; the client doesn't have equivalent coverage yet.
